# Lutista（本地定制版）

Android 端 LUT 滤镜批量处理 App，支持导入照片、叠加 LUT、调整色彩参数、批量导出，并带边框水印功能。

> 上游仓库：[qh7574/Lutista](https://github.com/qh7574/Lutista)
> 本仓库是上游源码的复刻 + 本地定制分支，包名 `cn.alittlecookie.lutista` 保持不变，方便与上游对照。

技术栈：Kotlin + Jetpack Compose + MIUIX + Room + Koin + Coil，图像处理走 Vulkan NDK（`app/src/main/cpp/vulkan_engine`，着色器 `unified.comp` 由 NDK 的 `glslc` 编译；仅 `arm64-v8a` 编译真实库，其余 ABI 走 `jni_bridge_stub.cpp`）。

## 一、本次定制内容

### 1. 底部滤镜行实时预览

底下一排滤镜卡片，原来是"灰底 + 滤镜名首字母"的占位块（`EffectItem.thumbnail` 在上游代码里恒为 `null`）。
现在每张卡片直接显示 **当前照片 × 该滤镜** 的真实渲染缩略图，翻照片、换滤镜、改参数都会跟着更新。

### 2. 整页平铺滤镜选择器

一组图标，点开是全屏平铺的滤镜面板。行列与每页个数**不是写死的**，而是每次按"可用屏幕空间 + 当前照片真实宽高比 + 滤镜个数"现算。

| 密度 | 目标格宽 | 行数上限 | 竖构图 3:4 实际结果 | 横构图 4:3 / 16:9 实际结果 |
|---|---|---|---|---|
| 大 | 190dp | 6 | 2 × 3，6 个/页 | 2 × 4 / 2 × 5，格子随图片变大变小 |
| 中（默认） | 126dp | 8 | 3 × 4，12 个/页 | 3 × 6 = 18 / 3 × 7 = 21 |
| 小 | 92dp | 10 | 4 × 5，20 个/页 | 4 × 5 ~ 4 × 6，只显示选中项的名字 |

算法（`FilterGridDensity.metrics()`）：

1. 列数 = max(最小列数, 按目标格宽能放下的列数) —— 屏幕越宽列越多，平板/横屏自动加密；
2. 格子宽 = 列宽，格子高 = 宽 ÷ 照片比例 —— 等价于 `Modifier.aspectRatio(aspect)`，任何比例（4:3、3:4、16:9、1:1、全景）都成立；
3. 行数 = 可用高度能放下的行数，且不超过"装完当前列表所需行数"，避免列表短时算出一堆空行；
4. 行高不够时整格等比缩小 —— 永远是完整图片，**不裁切、格子内不留白**。

所以换一张比例不同的照片，网格会自动重新排布，不需要改代码、也不需要为某种比例单独适配；界面顶部会实时显示当前实际行列（如"共 21 个 · 3×7"），底部显示"每页 N 个"。

- 左右滑动翻页（`HorizontalPager`），顶部可实时切换三档密度，底部有页码圆点和"每页 N 个"提示。
- 点击格子 = 选中该滤镜并关闭面板，选中态与底部横向行同步；当前选中的格子有描边 + 勾选角标。
- 打开时自动定位到当前选中滤镜所在的那一页；密度写入设置，下次打开沿用。
- 支持"默认"角标（全局默认滤镜）与渲染中的小转圈。
- 底部横向滤镜行的卡片高度同样按照片真实比例算（`88dp ÷ aspect`，40–168dp 之间夹一下），横图卡片自动变矮、竖图变高，不再固定方形。

### 3. 单张精修：点滤镜直接进配方室

软件核心是"监控文件夹 → 批量出片"，单张图的细化调节原先是死路：点了滤镜只能应用，不能调。现在：

- 首页"联机模式"旁保留并强化 **"从相册选择 · 单张精修"** 入口（副标题直接写明"选照片后点任意滤镜，可调强度 / 曲线 / 色彩 / 暗角 / 颗粒"）。
- 在单图处理界面**点任意滤镜**（底部横排或整页平铺格子都一样）→ 应用该滤镜，并**自动为该照片复制一份配方备份**（名称形如 `CyanOrganic · 单图备份`），随即进入配方室面板。同一个滤镜反复点不会重复备份，直接复用同一份。
- 配方室面板与"配方室"Tab 里的是**同一套界面**，因此支持全部能力：
  - LUT：全局 LUT 浓度、LUT 1 / LUT 2 双 LUT 叠加、两条独立浓度、替换 LUT 文件；
  - 亮度：曝光、对比、高光、阴影；
  - 颜色：饱和度、色温、色调；
  - 曲线：白 / R / G / B 四通道曲线编辑；
  - LCH（HSL）：红/橙/黄/绿/青/蓝/紫/肤色 8 组明度-彩度-色相；
  - 暗角、颗粒（强度/大小/影调分区）。
- 面板里的预览图**固定为你刚选的那张照片**，任何滑杆改动都实时反映到这张图上；返回时若改动未保存会提示"保存修改 / 放弃修改 / 继续修改"。
- 因为改动写在"单图备份"副本上，**原配方和实时监听用的默认滤镜不会被改动**；需要的话备份本身也能当普通配方在配方室继续用、导出或删除。

> 顺带修了一个实质 Bug：单图渲染此前只拷贝了配方的一部分字段（`lutPath*`、`lutConcentration*`、`lutPrecision`、曝光/对比/高光/阴影、饱和/色温/色调、暗角），**漏掉了全局 LUT 浓度、曲线、LCH、颗粒**，所以配方室里调好的曲线/HSL/颗粒在单图上根本不生效。现已统一由 `FilterEntity.toFilterConfig()` 完整转换，预览与导出用的是同一份参数。

### 4. 轻点套用 / 长按精调，备份不再堆在滤镜列表里

上一版是"点一下滤镜就弹配方室"，快速刷滤镜时要不停进进出出。这一版把两种意图拆开：

| 操作 | 行为 |
|---|---|
| 底部横排**轻点**卡片 / 网格**轻点**格子 | 只把滤镜套上去，画面立即变，不弹面板（网格顺手收起） |
| 底部横排**长按**卡片 / 网格**长按**格子 | 套用并直接进入精修面板（等价于原来的行为） |
| 预览右上角 **「精调参数」** 按钮 | 常驻入口，套了滤镜后一直可见；点它就调当前滤镜，不用记长按手势 |

网格面板底栏也加了一行提示"轻点套用 · 长按套用并精调"。

同时把"单图备份"从日常滤镜列表里摘出来：

- **底部横排、整页平铺、"放置"页的「滤镜选择」下拉都不再显示备份**，常用配方不会被挤到后面（实测整页平铺计数仍是 21 个而不是 24 个）。唯一的例外是**当前这张照片正在用的那一份**：它以 `源滤镜名 · 精修` 的形式插在源滤镜后面并处于选中态，这样改完参数保存后，横排里有一张卡片显示的就是"调整后的效果"。
- 配方室列表把备份统一排到最末，并加分组标题「单图备份」+ 一行说明，一眼能分清哪些是常用配方、哪些是给某张照片临时留的。
- **试一下但没保存的备份会自动清掉**：打开面板后一路没点保存就退出，这份副本会被删除，当前滤镜退回原配方，不会在配方室里留下一条"和原配方一模一样却没用的"条目。点过保存（含顶部菜单里的"保存"）则保留。
- 备份不再"套娃"：如果当前选中的本身就是一份备份（比如刚精修完又点「精调参数」），直接打开它，不会再生成一层 `… · 单图备份 · 单图备份`。

## 二、实现要点

参考项目是另一套工程（View / XML + RecyclerView + CPU 渲染），本项目是 Compose + Vulkan 单例引擎，**底层原理不同，所以只借思路、不搬代码**：

1. **基准图只解码一次**：当前照片按最长边 512 解码一份 RGBA（含 EXIF 方向纠正），之后所有滤镜复用这同一份字节，换滤镜不重复解码。
2. **一份最高版本，绘制时缩放**：每个滤镜只渲染并缓存一份 512 长边结果，小格子交给 Compose 绘制时缩放。
   - 好处：切"大 / 中 / 小"密度零重渲，没有"放大后重新渲染"的二次等待，也不会出现模糊过渡。
   - 对比"按档位分别渲染"：后者在 24 格档位要付 24 次渲染，且每次切档都要重来一轮，代价随格数线性增长。
3. **单 worker 串行渲染**：可见格子优先，其余按空闲补齐；滚动/翻页时低优先级请求会被跳过，换照片用 `generation` 丢弃过期结果。
4. **字节级 LRU**：上限 32MB / 96 张，淘汰时只从显示列表移除、不 `recycle`，避免正在绘制的帧崩溃。
5. **渲染锁**：`ImageProcessingEngine` 的三个预览入口统一加锁。Vulkan 引擎是进程内单例，LUT 纹理上传和 `processImage` 必须成对串行，否则主预览和缩略图并发时会用错 LUT。
6. **网格自适应**：官方 Compose 没有"按图片比例自动重排网格"的一键 API，需要用三个基础能力组合：
   - [`GridCells.Adaptive(minSize)`](https://developer.android.com/develop/ui/compose/lists#lazy-grids)——先给定目标格宽，再由网格自己算出能做几列（本项目手写分页，所以按同样的规则自己算列数）；
   - [`Modifier.aspectRatio`](https://developer.android.com/develop/ui/compose/graphics/images/customize#custom-aspect-ratio)——格子高度由图片宽高比决定；
   - [`ContentScale.Fit`](https://developer.android.com/develop/ui/compose/graphics/images/customize#content-scale)——默认缩放模式，等比缩放完整显示，不裁切；
   - 配合 [`BoxWithConstraints`](https://developer.android.com/develop/ui/compose/layouts/adaptive) 在运行时拿到可用宽高，把上面三条算成一屏的几何。
   这套组合在官方 [adaptive layouts](https://developer.android.com/develop/ui/compose/layouts/adaptive) 里就是"用运行时尺寸驱动布局"的标准做法。

### 构建命令

```bash
# JDK 21 未加入自动探测路径时，用 -D 显式指定
gradle :app:assembleDebug \
  -Dorg.gradle.java.home=/path/to/jdk-21 \
  -Dorg.gradle.java.installations.paths=/path/to/jdk-21 \
  -Dorg.gradle.java.installations.auto-download=false
```

国内网络访问 `dl.google.com` / `repo.maven.apache.org` 很慢时，用仓库自带的镜像脚本（只做本地构建辅助，不改动项目依赖声明）：

```bash
gradle :app:assembleDebug --init-script gradle/aliyun-mirror.init.gradle
```

只出一个 ABI 可以明显缩短构建时间：

```bash
gradle :app:assembleDebug -Pandroid.injected.build.abi=arm64-v8a
```

> PowerShell 下整条参数要加引号，否则会被拆成 `-Pandroid` + `.injected.build.abi=...`，报 `Task '.injected.build.abi=arm64-v8a' not found`。

产物：`app/build/outputs/apk/debug/app-debug.apk`（本仓库做了单 ABI 构建时，APK 落在 `app/build/intermediates/apk/debug/`）。

## 四、版本更新记录

### v1.3.3 · 2026-11-20

**性能（渲染管线）**
- **不再为每次渲染复制整幅图像**：引擎里新增一块跨调用复用的渲染缓冲。原来每渲一帧都要 `rgbaBytes.copyOf()` 现分配一份输入（512 长边 1.4MB / 1024 预览 5.6MB），换一张照片 20 多个滤镜就是 20 多次大分配；现在复制进同一块缓冲、为零新分配。超过 16MB 的整幅导出走一次性分配，不常驻。
- **原生侧就地返回**：Vulkan 本来就把结果写回入参那块内存，JNI 里那句 `NewByteArray` + `SetByteArrayRegion` 是多余的一整幅拷贝，已去掉，直接提交回 Java 数组。
- **配方配置记忆化**：`toFilterConfig()` 每次调用都要解析 曲线 / LCH / 颗粒 三段 JSON，缩略图成批渲染和拖滑杆时会成百次触发；现在按 `(id, updatedAt, json 指纹)` 缓存解析结果，配方室保存刷新 `updatedAt` 时缓存自然失效。
- **LUT 解析去装箱**：`mutableListOf<Float>` 改成预分配 `FloatArray` 直接写入，数据行判定从"每行跑一次正则"改成看首字符。33³ 的 .cube 解析 16.1ms → 9.2ms（桌面 JVM，1.7×；ART 上装箱开销更贵，收益更大），同时省掉约 10.7 万个 Float 临时对象。
- **统一 LUT 逐像素不再新建数组**：`trilinearInterpolation` 增加写入 `out[3]` 的重载，1024 长边一次渲染少约 140 万次 `FloatArray` 分配。
- **查表 O(1)**：`PhotoProcessScreen` 里 4 处 `filtersFromDb.find { ... }`、`indexOfFirst` 改成 `remember(filtersFromDb)` 建 `id → 配方` 的 Map；`getCurrentSettings()` 在未定制照片上回落到 `remember` 的默认实例，不再每次重组新造对象。

**稳定性（少崩溃）**
- **LUT 缓存加 LRU 上限（8 份）**：原来无上限，64³ 精度下每份展开 3MB float，滤镜一多内存只涨不落。
- **OOM 兜底**：缩略图渲染、基准图解码、主预览渲染、批量导出四条路径都补了 `OutOfMemoryError` 处理——内存不够时清掉缩略图缓存、跳过这一张，而不是直接把进程带走。
- **缩略图淘汰不再持锁写 Compose 状态**：锁内只改 LRU Map，被淘汰的 id 回到锁外再摘掉快照状态。

**说明**
- 版本号 `1.3.2` → `1.3.3`（versionCode 6 → 7）。功能与 v1.3.2 完全一致，只做性能/稳定性加固，无交互变化。

### v1.3.2 · 2026-11-20

**修复**
- **底部滤镜缩略图不跟随参数变化**：这是两个问题叠在一起。
  1. 缩略图渲染用的 `toPreviewFilterConfig()` 只映射了部分字段，**漏了全局 LUT 浓度、曲线、LCH、颗粒、统一 LUT**，所以配方室里把「全局 LUT 浓度」从 100% 拖到 40% 保存后，主预览变了、缩略图却怎么都不会变。现在缩略图与主预览共用同一套完整参数（`toPreviewFilterConfig()` 直接复用 `toFilterConfig()`）。
  2. `FilterThumbnailStore` 的缓存只按 `filterId` 做键、且定义了 `invalidate()` 却没人调用，参数改了旧图会一直留在缓存里。现在按 `FilterEntity.hashCode()` 记录每个滤镜的参数指纹，指纹变了立刻丢缓存重渲；渲染期间参数又被改过的，结果直接丢弃，不会把旧参数的图回填缓存。

**新增**
- 当前照片正在使用的那份「精修副本」会作为一张 **`源滤镜名 · 精修`** 卡片出现在底部横排（就排在它的源滤镜后面），并作为当前选中项高亮。以前这份副本被过滤掉，横排里没有任何一张卡片被选中，也看不到调整后的效果——"缩略图没刷新"的观感有一半来自这里。
- 其余备份仍然不进底部横排/整页平铺/首页「滤镜选择」，常用配方不会被挤下去。

**验证（MuMu 1080×2400 / 440dpi）**
- 同一张照片套 CyanOrganic（100%）→ 精调参数拖「全局 LUT 浓度」到 37% → 保存：横排出现 `CyanOrganic · 精修` 卡片并被选中，缩略图明显比 100% 那张更接近原图（缩略图区平均色 226,222,211 → 238,236,232，原图为 245,244,244）。
- 再次精调同一份副本到 81% → 保存：**同一张卡片**的缩略图就地刷新（238,236,232 → 229,225,217），而 100% 的 CyanOrganic 卡片全程不变（226,222,211）。

### v1.1.0 · 2026-11-19

**新增**
- 底部滤镜行实时预览：每张滤镜卡片显示"当前照片 + 该滤镜"的渲染缩略图，替代原来的首字母占位块。
- 整页平铺滤镜选择器：滤镜 Tab 新增网格入口，三档密度（大 / 中 / 小），左右滑动翻页，点击选中并与底部行同步；密度持久化保存。

**优化**
- `ImageProcessingEngine` 的三个预览入口统一加渲染锁，修复主预览与缩略图并发时 LUT 串扰的隐患。
- 缩略图渲染串行化 + 可见优先 + 空闲补齐 + 32MB/96 张字节级 LRU，翻页不卡、切档零重渲。
- 整页平铺面板补齐状态栏 / 导航栏安全区，标题不再被状态栏压住。
- 缩略图比例跟随原图：底部横排与三档网格的图片区都按原图宽高比计算并 `ContentScale.Fit` 显示，不再被裁切；格子尺寸等于图片尺寸、紧凑排列并整体居中，选中框紧贴图片，格子内部不再出现左右留白。
- 长按查看原图不再闪屏：主预览的两个状态改用同一个 Compose `Image` 槽位切换 `ImageBitmap`，不再经过 Coil 的异步重载（原实现切状态时图片会先空一帧）。
- 三档密度重定（真机反馈驱动）：原来只改列数、不改行数，格子大小实际由行高决定，导致"大档和中档格子一样大、大档横向还少一个"；改为让三档同时具备目标格宽与行数上限，格子尺寸依次递减。
- 小档改为每排 5 个（原 4×6 左右留白过大）。第二轮真机反馈仍偏小，最终小档定为每排 4 个（4×5 = 20 个/页，格子 86×115dp，比 5 列时放大约 60%）。
- 网格改为运行时自适应（不再固定 2×3 / 3×4 / 5×5）：列数按目标格宽与屏幕宽度算，行数按可用高度与照片真实比例算，每页个数随比例浮动；换横图、竖图、方图、全景图都不需要改代码。竖构图 3:4 下的结果与原来一致（2×3、3×4、5×5）。
- 底部横向滤镜行的卡片高度改为按照片真实比例计算（原为固定方形卡片 + 56–120dp 夹取）。
- 版本号 `1.0` → `1.1.0`（versionCode 1 → 2）。

**已知限制**
- 实时预览目前只覆盖"滤镜" Tab；"边框水印" Tab 的列表仍为文字卡片。
- 缩略图按滤镜的**已保存参数**渲染，拖动当前滤镜的滑杆时，主预览实时变化而该卡片缩略图保持旧样（避免拖动时反复重渲）。
- 横屏 / 平板上行高受限时，图片按比例居中、两侧留白（不裁切是优先取舍）。
